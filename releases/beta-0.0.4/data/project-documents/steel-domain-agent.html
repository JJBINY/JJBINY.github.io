Steel Domain AI Agent

철강 제조 현장의 공식 문서, 작업 경험, 설비 상태를 연결해 근거가 있는 가이던스와 분석 리포트를 제공하는 AI 시스템

프로젝트 개요

철강 제조 현장의 질문은 공식 절차만으로 해결되지 않는 경우가 많습니다. PDF 작업표준과 표·그림, 현장 노하우, 현재 설비 상태를 서로 다른 방식으로 구조화하고, 하나의 질문 흐름에서 필요한 근거를 찾아 최종 답변으로 정리하는 시스템을 구축했습니다.

구분 내용
적용 대상 설비·공정 절차 확인, 문제 원인 탐색, 조치 가이던스, 운영 분석
입력 사용자의 자연어 질문과 대화 맥락
활용 정보 공식 메뉴얼, 작업 노하우, Digital Twin 상태·분석
출력 출처가 연결된 가이던스 또는 분석 리포트
주요 구현 질문 해석, 작업 계획, 전문 Agent 실행, 근거 검증, 최종 답변 작성

전체 시스템 아키텍처

설명 모델 — 현재 저장소의 구성요소와 근거 흐름을 포트폴리오용으로 단순화한 그림

이 그림은 질문이 들어온 뒤 필요한 작업을 정하고, 여러 지식원에서 근거를 수집한 다음 하나의 답변으로 만드는 전체 흐름을 보여줍니다. Agent는 시스템 전체가 아니라 공식 문서, 현장 경험, 설비 상태를 각각 담당하는 전문 실행 구성요소입니다.

주요 구성요소

구성요소 역할
질문 해석 질문의 대상, 목적, 조건, 대화 맥락 파악
작업 구조 답변에 필요한 정보와 작업 관계 표현
실행 계획 변환 작업 구조를 실제 실행 순서와 병렬 작업으로 변환
실행 조정 Agent 호출, 실행 순서, 병렬 처리, 실패와 재시도 관리
전문 Agent 담당 지식원 검색과 결과 해석
근거 저장소 출처, 위치, 적용 조건이 연결된 근거 보관
답변 작성 채택된 근거를 인용 가능한 가이던스·리포트로 구성

활용 지식

지식원 제공 정보
공식 메뉴얼 작업 절차, 규정, 설비 설명
작업 노하우 현장 사례와 문제 해결 경험
Digital Twin 설비·공정의 현재 상태와 분석 결과

설비, 공정, 현상, 조치 사이의 관계는 도메인 지식 체계로 관리합니다. 이 관계 정보는 질문을 이해하고 필요한 지식원을 선택하는 데 사용하며, 최종 답변의 출처는 실제 메뉴얼·노하우·Digital Twin 결과에 연결합니다.

비정형 지식 전처리

PDF와 노하우 원천을 각각 구조화한 뒤 검색용 Passage와 인용용 Source Fragment를 분리하는 흐름.

원천 전처리 시스템에서 사용하는 형태
작업표준 PDF OCR·layout 분석, 표·그림 Data-to-Text, 번호·절 구조 복원 Document–Chunk–Element, 검색 Passage, page·bbox가 있는 Source Fragment
현장 노하우 행·사례 단위 정규화, 공정·설비·현상·조치 binding source-bound 사례, 적용 범위, 관계 강도와 검수 상태
Digital Twin 설비·지표·시간 범위 binding과 조회 계약 검증 시점과 dataset이 붙은 typed artifact

검색 본문에는 의미와 검색에 필요한 표현을 두고, 원문 행·셀·번호·좌표는 별도 locator로 보존했습니다. 이 분리로 검색 recall을 높이기 위한 표현이 실제 인용 위치를 대신하지 않도록 했습니다.

도구·Agent·Orchestrator 구조

도구, 전문 Agent, Orchestrator가 소유하는 판단 범위를 분리한 흐름.

계층 담당 범위
조회 도구 문서 검색, 원문 위치 조회, 노하우 검색, 설비 상태 조회
전문 Agent 임무에 맞는 검색 계획, 도구 호출, 후보 검증, 근거 제안
Orchestrator 사용자 질의의 작업 계획, Agent 선택, fan-out/fan-in, 실패 처리
근거 원장·답변 계층 출처와 작업이 결합된 근거 채택, 인용 가능한 최종 응답 생성

단일 검색 도구에서 시작한 구조를 Search Agent의 계획·해석 경계로 확장하고, 다시 메뉴얼·노하우·Digital Twin Agent를 조정하는 전체 시스템으로 결합했습니다. 코드에서는 이 역할이 Conversation Runtime, Query Understanding, compiler, Executor/Coordinator로 나뉘며, 포트폴리오에서는 이 조정 책임을 Orchestrator로 설명합니다.

E2E Agent Loop

한 요청이 질의 이해, HITL, 계획, Agent 실행, 근거 채택, 최종화로 이어지는 전체 흐름.

단계 처리 내용
질의 이해 원문과 대화 맥락 보존, 용어·도메인 grounding, 구조화된 Semantic Request 생성
HITL 설비·문서 범위처럼 결과를 바꾸는 모호성만 선택지와 함께 확인하고 같은 질의 이해 경로로 재진입
계획 의미 작업 관계를 TaskGraph로 표현하고 capability·dependency·budget이 있는 ActionGraph로 컴파일
Agent 실행 메뉴얼·노하우·Digital Twin 임무를 제한된 병렬성으로 실행하고 typed receipt 수집
근거 채택 task binding, source locator, 적용 범위를 통과한 결과만 accepted evidence로 기록
최종 응답 답변 계획, Answer IR, 인용과 입력 digest 검증을 거친 가이던스·리포트 생성

검색 결과가 없거나 답변에 사용할 근거가 부족한 경우에는 제한된 횟수의 재검색을 수행합니다. 이후에도 중요한 모호성이 남으면 사용자 확인이 필요한 항목으로 분리합니다.

주요 구현

  • 질문 의미 모델과 대화 맥락 처리
  • PDF·표·그림·현장 사례의 source-bound 전처리
  • 검색용 Passage와 인용용 Source Fragment 분리
  • 의미 기반 작업 구조(TaskGraph)
  • 실행 계획(ActionGraph)과 실행기
  • 공식 문서·현장 경험·설비 상태 Agent
  • Agent 실행 조정과 병렬 결과 통합
  • 출처·주장·적용 범위를 보존하는 근거 저장소
  • 절차 순서와 조건을 반영한 답변 구성
  • Runtime API, MCP 도구, 웹 인터페이스 통합
  • 실행 추적과 진행 상태 제공
